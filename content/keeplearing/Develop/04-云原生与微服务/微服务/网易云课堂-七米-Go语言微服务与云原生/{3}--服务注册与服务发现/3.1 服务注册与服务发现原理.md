## 技术原理
### 服务注册与服务发现是什么
**服务注册**：保存联系人——把xx的手机号保存到通讯录里。
**服务发现**：查找联系人——通过通讯录中xx的名片找到xx的手机号。
**注册中心（服务注册表）**：通讯录。

服务使用者通过唯一的 DNS 条目与 Web 服务进行通信：
![PixPin_2026-01-09_16-20-54.png](https://tyrese-1317134930.cos.ap-shanghai.myqcloud.com/imgs/blog/20260109162057275.png)

Web 服务的一个新实例使用其 IP 地址和端口向注册中心注册自己，当新实例注册成功后，它们将加入负载均衡池，以处理服务使用者请求：
![PixPin_2026-01-09_16-22-56.png](https://tyrese-1317134930.cos.ap-shanghai.myqcloud.com/imgs/blog/20260109162301069.png)

随着服务的新实例的添加和旧的或不健康的服务实例的删除，注册中心会动态更新。已删除的服务将不再参与用于处理服务使用者请求的负载均衡池：
![PixPin_2026-01-09_16-24-41.png](https://tyrese-1317134930.cos.ap-shanghai.myqcloud.com/imgs/blog/20260109162443683.png)

### 为什么使用服务发现？
在微服务的架构下，服务调用方无法精准的知道哪些服务实例提供服务，只能借助服务发现机制。
![PixPin_2026-01-09_21-12-25.png](https://tyrese-1317134930.cos.ap-shanghai.myqcloud.com/imgs/blog/20260109211228750.png)

## 服务发现的两种模式
### 客户端服务发现——服务及其调用方直接与注册中心交互
![PixPin_2026-01-09_21-16-49.png](https://tyrese-1317134930.cos.ap-shanghai.myqcloud.com/imgs/blog/20260109211651615.png)

**步骤：**
1. 查：服务调用方去服务注册表中查询对应服务实例有哪些IP和端口
2. 返：服务注册表返回对应服务实例的IP和端口号
3. 请求：从服务注册表返回的IP列表中选取一个IP地址发起请求

**服务注册表是如何知道有哪些实例提供服务的？**
各个服务实例在启动后，会向服务注册表发送服务注册请求，即可保证客户端每次在查询时都能获取到一个准确的实例IP地址。若某些服务实例挂了，由于注册中心与服务实例间存在心跳等机制，服务实例挂后就会被踢出服务注册表中。

**优势：**
支持多平台、各式服务的服务发现。不依赖于任何平台。
**劣势：**
需要在服务端和客户端集成SDK，并且要维护相关代码逻辑，需要考虑SDK的多语言支持。

### 服务端发现模式——通过部署基础设施来处理服务发现
![PixPin_2026-01-09_21-29-12.png](https://tyrese-1317134930.cos.ap-shanghai.myqcloud.com/imgs/blog/20260109212914648.png)
**步骤：**
1. 请求：服务调用方向平台路由器发起查询请求
2. 查&路由：平台路由器在接收到调用方发来的请求后，会像服务注册表发起查询请求，用于查询请求服务实例的IP地址和端口号。平台路由器在接收到服务注册表返回的IP地址后再根据平台事先定义的负载均衡策略将调用方的请求路由到服务实例上去。 

**服务注册表是如何知道有哪些实例提供服务的？**
每当有一个新的服务实例启动后，部署平台的注册器就会识别到新启动的服务实例，然后将其更新至服务注册表中，确保每次服务调用方在请求时都能拿到最新的服务实例列表。这是由第三方注册来实现服务发现的，区别于客户端服务发现的自注册模式

**优势：**
服务发现的所有方面都由平台处理，服务端和客户端都不包含任何服务的代码。
**劣势：**
仅限于使用该平台部署的服务，依赖于公司内部的基础设施支撑。
多一次网络跳转，存在性能损耗。
