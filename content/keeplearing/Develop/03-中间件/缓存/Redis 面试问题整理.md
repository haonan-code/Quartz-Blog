## 一、常规问题
#### 1. 什么是 redis，为什么要使用它？
Redis（Remote Dictionary Server） 是一个**基于内存**的键值对存储系统，常用作缓存服务。
redis 有如下特点：
- **读写性能优异：** Redis 以其**极高的性能**而著称，能够支持每秒数十万次的读写操作。这使得Redis成为处理高并发请求的理想选择，尤其是在需要快速响应的场景中，如缓存、会话管理、排行榜等。
- **数据类型丰富：** Redis 不仅支持基本的键值存储，还提供了丰富的数据类型，包括字符串、列表、集合、哈希表、有序集合等。这些数据类型为开发者提供了灵活的数据操作能力，使得Redis可以适应各种不同的应用场景。
- **原子性操作：** Redis 的所有操作都是原子性的，这意味着操作要么完全执行，要么完全不执行。这种特性对于确保数据的一致性和完整性至关重要，尤其是在高并发环境下处理事务时。
- **持久化：** Redis 可以通过**定期快照**或者**实时记录写操作日志**的方式将内存中的数据持久化到硬盘，确保数据在重启后不会丢失。
- **支持发布/订阅模式：** Redis 内置了发布/订阅模式（Pub/Sub），允许客户端之间通过消息传递进行通信。这使得 Redis 可以作为消息队列和实时数据传输的平台。
- **单线程模型：** 尽管 Redis 是单线程的，但它通过高效的事件驱动模型来处理并发请求，确保了高性能和低延迟。单线程模型也简化了并发控制的复杂性。
- **主从复制：** Redis 支持主从复制，可以通过从节点来备份数据或分担读请求，提高数据的可用性和系统的伸缩性。
- **应用场景广泛：** Redis 被广泛应用于各种场景，包括但不限于缓存系统、会话存储、排行榜、实时分析、地理空间数据索引等。
- **社区支持：** Redis 拥有一个活跃的开发者社区，提供了大量的文档、教程和第三方库，这为开发者提供了强大的支持和丰富的资源。
- **跨平台兼容性：** Redis 可以在多种操作系统上运行，包括 Linux、macOS 和 Windows，这使得它能够在不同的技术栈中灵活部署。

#### 3. redis 为什么快？
redis 从底层到设计理念都**为性能而生**，主要有以下原因：
- **纯内存存储**：所有数据都存储在内存中，读写速度极快，避免了磁盘 I/O 的开销。
- **单线程模型**：
	- Redis 采用单线程处理命令，避免多线程带来的上下文切换、锁开销；
	- 对于 CPU 和内存操作占主导的场景，单线程 + 高效事件循环更快。
	> ❗ 说明：Redis 只在处理命令时是单线程，**持久化（RDB/AOF）是多线程的**，从 Redis 6.0 起还引入了 I/O 多线程支持。
- **高效的数据结构**：Hash、ZSet、List 等都经过精心优化
- **I/O 多路复用（epoll）**：使用 `epoll`（事件驱动模型） 实现高并发连接处理
- **命令执行高效**：Redis 命令大多是 O(1) 或 O(logN) 时间复杂度
- **无磁盘 I/O 阻塞**：主要操作不涉及磁盘，避免慢速硬盘读写
- **网络协议极简**：RESP 协议格式简单，编解码效率高
- **操作大多为 O(1) 或 O(logN)**：常见命令如 `GET`、`SET`、`HGET`、`LPUSH` 都是 O(1)，非常快。即使像 `ZADD` 这种排序操作，也采用了跳表，能保持 O(logN) 性能。
#### 4. 说说Redis单线程模型
##### 介绍
> Redis 的**网络请求处理和命令执行**都是通过**单线程完成的**，也就是说：  
    **一个线程串行地处理所有客户端请求**。

但它不是完全单线程，**后台任务（如持久化、异步删除、复制）是多线程处理的**
##### 为什么 Redis 使用单线程反而更快？
**1.避免锁竞争**
- 多线程模型需要处理线程间锁同步问题，会带来**上下文切换**、**死锁风险**等。
- Redis 单线程没有锁，代码简单，效率高。
**2.事件驱动+I/O 多路复用（epoll）**
- Redis 用的是 **Reactor 模型 + epoll（Linux）/select（其他）**；
- 单线程通过监听多个 socket 事件，同时处理成千上万的连接。
**3.命令执行效率高**
- Redis 命令设计大多是 **O(1)** 或 **O(logN)**，执行快；
- 内部数据结构经过精心优化（如跳表、压缩链表等）。
**4.大多数操作是内存操作**
- 不涉及磁盘 IO，不会阻塞线程；
- 内存访问速度极快（纳秒级）。
#### 5. Redis 用来做什么
Redis 是一个基于内存的高性能键值数据库，主要用来解决高并发和高性能问题。  
典型的应用场景包括：
- **缓存**：降低数据库压力，提高查询性能
- **分布式锁**：防止并发修改导致数据不一致
- **限流与计数**：防止系统被恶意请求打挂

- **异步队列**：削峰填谷，解耦系统
- **延时任务**、**会话管理**、**全局 ID 生成** 等  
    在高并发系统中，Redis 往往与 MySQL 配合使用，承担“高性能缓存 + 并发控制 + 实时统计”的角色。

## 三、持久化和内存
#### 1. Redis 的持久化机制是什么？各自的优缺点？一般怎么用？
Redis 提供了两种核心的**持久化机制**：`AOF`（Append Only File）和 `RDB`（Redis DataBase）。它们负责将 Redis 的内存数据持久化到磁盘，防止数据丢失，保证数据恢复能力。
##### RDB（Snapshot 快照持久化）
定期**快照**式持久化（快照整个内存）

**说明：**
- Redis 会将当前所有数据生成一个 `.rdb` 二进制快照文件保存到磁盘
- 默认文件：`dump.rdb`
**启动方式：**
- 自动触发（默认规则：如 900 秒内有 1 次写入）
- 手动触发：`SAVE` / `BGSAVE`
**优点：**
- **启动速度快**：恢复时直接加载 RDB 文件即可
- **文件小**：二进制格式，体积精简，适合做全量备份
- **性能好**：主线程无阻塞，子线程执行持久化
**缺点：**
- **非实时**：只能定期保存，如中间宕机会丢失最近数据
- **不适合频繁写入的数据**：快照频繁会增加磁盘和 CPU 负担
##### AOF（Append Only File 追加日志）
**每次写操作追加**到日志文件中（类似 binlog）

**说明：**
- 每次执行写命令（如 `SET`、`DEL`）都会被追加到 `appendonly.aof` 文件中
- 启动时按日志**重放命令**恢复数据
**配置方式：**
```bash
appendonly yes
appendfsync always | everysec | no
```
**优点：**
- **更可靠**：日志实时记录写操作，数据几乎不丢（尤其设置 everysec）
- **可读**：AOF 是纯文本命令，手动编辑修复更方便
- **可增量恢复**：不像 RDB 一次性全量快照
**缺点**：
- **文件大**：长期运行会生成很大的日志文件
- **恢复慢**：启动时需要重放全部命令
- **写入频繁时稍慢**：I/O 开销比 RDB 大

##### 混合模式：AOF + RDB（推荐）
从 Redis 4.0 起，支持同时开启 AOF 和 RDB：
- 优先使用 AOF 恢复（数据更新）
- 如果 AOF 文件损坏 → 回退使用 RDB
- Redis 提供 AOF 重写（rewrite）机制，合并日志避免膨胀
##### 对比总结

| 特性    | RDB       | AOF                  |
| ----- | --------- | -------------------- |
| 持久化方式 | 定期快照      | 日志追加                 |
| 数据安全性 | 可能丢失几分钟数据 | 丢失 1 秒以内数据（everysec） |
| 启动速度  | 快         | 慢（命令多）               |
| 文件体积  | 小         | 大                    |
| 是否可读  | 否（二进制）    | 是（文本）                |
| 恢复过程  | 加载快照      | 重放命令                 |
| 推荐场景  | 定时全量备份    | 高可靠写入场景              |
#### 2. Redis 过期键的删除策略有哪些
Redis 对设置了 TTL（Time To Live）的 key，采用以下 **三种策略组合**来删除过期 key：
##### 1. 定时删除（定点删除）
- Redis 会在设置 key 的时候，**记录一个过期时间点**。
- 到了过期时间点后，不会立即删除，而是“**标记为过期**”。
> 但不会立刻被移除，除非被访问，或者被后台任务扫描到。
##### 2. 惰性删除（访问时判断）
每次客户端访问某个 key 时（如 GET/SET），Redis 会检查：
- 如果这个 key 有过期时间，且已经过期，则**立即删除**该 key。
- 如果没过期，就正常返回。
**优点**：节省 CPU，不用主动找过期 key
**缺点**：如果一个 key 从未被访问，就**不会被删除**，可能造成内存泄漏
##### 3. 定期删除（随即采样+批量删除）
Redis 默认每隔 `100ms` 会运行一次**定期任务**，从设置了过期时间的 key 中：
- 随机挑选一部分（默认 20 个）；
- 删除其中已过期的；
- 如果发现过期 key 比例 > 25%，继续进行循环清理，直到比例降下来。
> 这是 Redis 的主力清理方式，负责**防止大量过期 key 堆积**

## 五、集群
### 5.1 主从复制
#### 1. Redis集群的主从复制模型是怎样的？
Redis 的 **主从复制（Replication）** 是一种 **数据同步机制**，允许一个 Redis 实例（主节点）将数据复制到一个或多个 Redis 实例（从节点），实现 **读写分离、高可用、故障恢复** 等功能。
#####  基本概念
- **主节点（Master）**：负责处理写请求，同时将数据同步给从节点。
- **从节点（Slave/Replica）**：只读，复制主节点的数据，不处理写操作（默认）。
- Redis 6.0+ 开始使用 **Replica** 替代 Slave 表述。
#####  原理
**初次复制（全量复制）**
1. 从节点向主节点发送 `PSYNC` 命令（或老版本用 `SYNC`）。
2. 主节点执行 `BGSAVE`，生成 RDB 快照，同时缓存写命令。
3. 主节点将 RDB 文件传输给从节点。
4. 从节点加载 RDB 文件，恢复数据。
5. 主节点将缓存的写命令发送给从节点应用，保持数据一致。

**增量复制（断线重连）**
1. 主节点维护一个 **复制偏移量 offset** 和 **复制积压缓冲区（replication backlog buffer）**。
2. 如果从节点断线时间不长，重连后可以通过 offset 比对，直接从 backlog 中拉取丢失的数据，进行**增量同步**，避免全量复制。
#####  主从配置方法
配置从节点连接主节点
方法一：配置文件
```bash
replicaof 127.0.0.1 6379
```
方法二：运行时命令
```bash
127.0.0.1:6380> replicaof 127.0.0.1 6379
```
> 要取消复制，可以执行：`replicaof no one`

#####  主从架构模式
**1.一主一从（最基础）**
- 简单，提升读性能，有备份能力。
**2.一主多从（常见）**
- 多个从节点同步主节点，实现读写分离，负载均衡。
**3.级联复制（链式）**
```bash
Master
  |
Slave1
  |
Slave2
```
- Slave2 复制 Slave1，适用于跨机房部署，减少带宽压力。
#####  主从复制优缺点
**优点**：
- 提高读取性能
- 数据冗余，提高安全性
- 支持热备、故障恢复
**缺点**：
- 主从数据有同步延迟（秒级）
- 主节点宕机后，从节点不能自动提升为主（需要 Sentinel 或手动）
- 默认从节点不可写（防止数据不一致）
#####  常用命令

| 命令                        | 作用                                 |
| ------------------------- | ---------------------------------- |
| `replicaof <host> <port>` | 设置主节点                              |
| `replicaof no one`        | 取消复制，变成主节点                         |
| `info replication`        | 查看主从状态                             |
| `slaveof`                 | Redis 5.x 前的命令，6.0+ 用 replicaof 替代 |
#####  配合使用：Redis Sentinel（高可用）
- Redis 自身的主从复制不支持自动主从切换。
- 可使用 **Redis Sentinel** 实现主节点宕机后的 **自动故障转移**（Failover）。
- 也可结合 Redis Cluster 实现高可用和分片。

##### 实现 Redis 分布式锁的3种方式
**方式一：使用`SET NX PX`实现简单可靠的分布式锁**
**核心命令**：
```bash
SET lock_key unique_value NX PX 30000
```
**说明**：
- `NX`：只在 key 不存在时设置（实现加锁）
- `PX 30000`：设置锁过期时间（毫秒）防止死锁
- `unique_value`：标识请求者身份（用于解锁时比对）
**加锁逻辑**（伪代码）
```go
success := redisClient.Set(ctx, "lock:order:123", uniqueID, "NX", "PX", 30000).Result()
if success == "OK" {
    // 获取锁成功，执行业务逻辑
}
```
**解锁逻辑（必须保证只释放自己加的锁）**
使用 Lua 脚本原子性释放：
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```
调用：
```go
script := `if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`
redisClient.Eval(ctx, script, []string{"lock:order:123"}, uniqueID)
```
**为什么不能直接 `DEL` 解锁？**
因为多个客户端可能互相覆盖锁，**直接删除会误删别人的锁！**
必须**比对锁的 value（唯一标识）后才能删除**，所以要用 Lua 脚本确保原子性。
**可选：自动续期机制（Watchdog）**
为了处理任务执行时间超过锁过期时间，可以使用 Watchdog 自动续期：
- 后台定时检查自己持有的锁是否快过期，自动 `PEXPIRE`
- Go 实现可以用 goroutine+定时器
**方式二：使用 Redlock（Redis 官方多节点锁）**
**原理**：
在 **多个 Redis 实例（如5个）中加锁成功 >= 3 个**，才认为成功。
**流程**：
1. 获取当前时间 `start_time`
2. 顺序对多个 Redis 节点执行 `SET NX PX`
3. 统计成功实例数 ≥ N/2 + 1 且时间未超时 → 加锁成功
4. 解锁时发到所有节点执行 `DEL` 脚本
**优点**：
- 容错性更高
- 抗 Redis 节点宕机
**缺点**：
- 实现复杂，需多个 Redis 实例
- 分布式部署才有优势
**常用库**：
- Java：Redisson
- Python：redis-py Redlock
- Go：`bsm/redislock`
**方式三：基于 Redis 的队列锁/信号量锁（List/Stream 模拟锁）**
**原理**：
利用 Redis 的数据结构实现「排队加锁」或「限量加锁」：
**场景1：队列式互斥锁（公平锁）**
用 `LPUSH` + `BRPOP` 实现一个排队系统：
```bash
LPUSH lock_queue client_id
BRPOP lock_queue 0  # 阻塞直到自己排到队首
```
- 客户端排队等待获取锁
- 可以实现公平锁（先来先得）
**场景2：限量信号量（Semaphore）**
假设只允许 3 个客户端同时执行某操作：
```bash
ZADD semaphore now timestamp client_id
ZREMRANGEBYSCORE semaphore -inf (now - timeout)
ZCARD semaphore
```
- 用 `ZADD` 模拟一个过期的令牌桶
- 控制同时访问人数不超过阈值
✅ 优点：
- 灵活，适用于并发控制（排队/限流/资源控制）
- 支持公平性、限量控制等业务场景
❌ 缺点：
- 实现更复杂
- 一般不直接用于纯分布式锁，而是配合业务控制

#### 6. redis 缓存有哪些问题，如何解决
#### 7. Redis 缓存击穿、雪崩、穿透发生原因以及应对/解决方案
##### 缓存雪崩（Cache Avalanche）
**定义：**
> 大量缓存同时过期/失效，导致所有请求都打到数据库上，数据库被压垮。

**发生原因：**
- Redis 中很多 key 设置了**相同或相近的过期时间**
- 某个时间点，大量 key 同时失效
- 所有请求瞬间访问数据库
**应对方案：**

| 方法               | 说明                                    |
| ---------------- | ------------------------------------- |
| ✅ **过期时间加随机值**   | 避免 key 同时过期，比如 `expire + rand(0~60秒)` |
| ✅ **设置热点数据永不过期** | 只手动更新，防止大面积过期                         |
| ✅ **限流 + 降级**    | 比如使用 `hystrix`/`sentinel`，保护数据库       |
| ✅ **预热缓存**       | 服务启动时提前将热点数据加载进缓存                     |

##### 缓存击穿（Cache Breakdown）
**定义：**
> 某个“热点 key”突然失效，短时间内大量并发请求访问这个 key，瞬间压垮数据库。

**发生原因：**
- 热点 key 过期或被删除了
- 很多请求正好同时请求这个 key，打到数据库
**应对方案：**

| 方法                         | 说明                     |
| -------------------------- | ---------------------- |
| ✅ **加互斥锁/分布式锁**            | 同一时间只允许一个请求去加载数据库，其他等待 |
| ✅ **热点 key 永不过期 + 主动刷新机制** | 热点 key 不设置 TTL，后台定期更新  |
| ✅ **使用本地缓存（兜底）**           | 增加一层本地缓存，用于短期兜底        |
| ✅ **提前异步刷新**               | 检测 TTL 快到期就提前异步刷新 key  |

##### 缓存穿透（Cache Penetration）
**定义：**
> **客户端请求了**数据库和缓存都不存在的 key，**每次都绕过缓存打到数据库**。

**发生原因：**
- 恶意攻击请求随机不存在的 key（如 id = -99999）
- key 不存在，缓存中也没有
- 数据库查不到，无法缓存，下一次还会查数据库 → 无限循环
**应对方案：**

| 方法                        | 说明                                 |
| ------------------------- | ---------------------------------- |
| ✅ **缓存空值/标记**             | 查询数据库返回空，也缓存一个标识值，如 `""`，并设置较短 TTL |
| ✅ **布隆过滤器（Bloom Filter）** | 初始化加载所有合法 key，在查询前先判断 key 是否可能存在   |
| ✅ **参数校验/黑名单拦截**          | 比如判断 id 是否 < 0，或者拦截高频恶意 IP 请求      |

#### 8. Redis使用的场景，怎么保证缓存和数据库的一致性问题,有一般几种方法,把详细过程说明一下?
##### 为什么会数据不一致？
数据不一致的场景主要发生在：
- **写操作后更新不及时**
- **并发场景下读写冲突**
- **缓存过期/删除失败**
##### 一致性保障策略
**1.缓存更新策略**

| 策略名称                | 描述                                       | 特点               |
| ------------------- | ---------------------------------------- | ---------------- |
| Cache Aside（旁路缓存）   | 应用先从 Redis 查找缓存，查不到再查 MySQL，并将结果写入 Redis | **最常见方案**，适合读多写少 |
| Read Through（读穿缓存）  | 应用只访问 Redis，Redis 查不到自动从 DB 获取并缓存        | Redis 负责加载逻辑     |
| Write Through（写穿缓存） | 应用更新操作直接写入 Redis，Redis 再写入 MySQL         | 写路径较慢，但一致性好      |
| Write Behind（写回缓存）  | 先写 Redis，再异步写 MySQL                      | 一致性最弱，但写性能高      |

**2.删除缓存 or 更新缓存**
更新 MySQL 后，缓存如何处理？
- ✅ **删除缓存（推荐）**：更新数据库后 **删除缓存**，下次读时触发缓存刷新（延迟加载，减少一致性问题）
- ❌ **直接更新缓存**：容易在并发或失败时导致缓存和数据库不一致

**3.操作顺序问题**
更新 DB 和 Redis 的顺序非常关键，推荐流程如下：
✅ 推荐顺序（延迟双删策略）：
```bash
删除缓存（第一次）
更新数据库
睡眠几十毫秒
再次删除缓存（防止并发读旧值）
```
📝 延迟双删的目的：解决并发导致的脏数据问题。
**4.分布式锁保障一致性（防止并发冲突）**
- 利用 Redis 的分布式锁（如 `SETNX + EXPIRE` 或 Redisson）
- 适用于高并发读写场景，防止多线程同时写入导致脏数据

**5.异步消息队列（MQ）方案**
- 将更新操作发到 MQ，监听器去更新缓存
- 能处理高并发、异步一致性
- 通常用于最终一致性要求场景

**6.过期机制 + 定期修复**
- Redis 设置合理的过期时间
- 后台定期任务（如定时对账）校验 Redis 和 MySQL 数据一致性，及时修正

#### 10. 给你一个 redis 和 mysql 如何设计他俩之间的缓存同步
##### 缓存失效策略（Cache Aside）+ 延迟双删 + 分布式锁（可选）
**实现步骤：**
场景：更新一个用户信息接口（`/updateUser`）

**步骤一：查询时从缓存查，没有再查数据库并写入缓存**
```go
// 查询用户信息
func GetUserInfo(userID int64) (*User, error) {
    key := fmt.Sprintf("user:%d", userID)
    data, err := redisClient.Get(ctx, key).Result()
    if err == redis.Nil {
        // Redis没有数据，从数据库查
        user, err := db.FindUserByID(userID)
        if err != nil {
            return nil, err
        }
        // 写入Redis缓存
        redisClient.Set(ctx, key, marshal(user), time.Hour)
        return user, nil
    } else if err != nil {
        return nil, err
    }

    return unmarshal(data), nil
}
```

**步骤二：更新操作 - 删除缓存 + 更新数据库 + 延迟再删一次缓存**
```go
// 更新用户信息
func UpdateUser(user *User) error {
    key := fmt.Sprintf("user:%d", user.ID)

    // 第一次删除缓存
    redisClient.Del(ctx, key)

    // 更新数据库
    err := db.UpdateUser(user)
    if err != nil {
        return err
    }

    // 延迟双删（短暂睡眠后再删一次）
    go func() {
        time.Sleep(50 * time.Millisecond)
        redisClient.Del(ctx, key)
    }()

    return nil
}
```

**分布式锁（可选）防止缓存击穿或并发写**
> 如果多个请求同时导致缓存失效并打到数据库，可加锁防止并发读写。

```go
lockKey := fmt.Sprintf("lock:user:%d", userID)
ok, _ := redisClient.SetNX(ctx, lockKey, 1, time.Second*5).Result()
if !ok {
    // 获取锁失败，可以重试或直接返回
}
defer redisClient.Del(ctx, lockKey)
```

**进阶方案：使用消息队列同步缓存（最终一致性）**
> 写数据库后，发送缓存更新事件到 MQ，消费者监听后异步更新/删除 Redis 缓存。

```bash
应用 => 写 MySQL => 发送 MQ 事件 => 缓存服务消费事件 => 更新或删除 Redis
```
适合：
- 异步任务处理
- 缓存数据更新依赖多个表或业务逻辑
- 追求解耦

**补充方案：定时任务修复 + 数据校验**
- 定期全量/增量扫描数据库与缓存比对
- 适合关键业务做兜底保障（定时任务 + diff工具）

#### 11. 在一个业务中需要多次查询 redis 时怎么优化?(pipeline) 如果有一大批 redis 命令 怎么优化
> 有大量 Redis 命令时，**首选 Pipeline 批量发送 + 批量命令合并 + 本地缓存补充**，极大优化性能，避免 Redis 成为瓶颈
##### 优化策略总览

| 类别     | 策略                    | 说明                        |
| ------ | --------------------- | ------------------------- |
| 减少请求次数 | 批量操作（MGET）            | 一次请求获取多个 key 的值           |
| 减少重复请求 | 本地缓存                  | 将频繁访问的数据短暂存本地，减少 Redis 请求 |
| 合理数据结构 | 使用 Hash/Set/List/ZSet | 减少多个 key 的维护              |
| 并发访问优化 | Pipeline              | 多命令合并发送，减少网络开销            |
| 数据预热   | 启动或高峰期预加载热点数据         | 避免冷启动查询慢                  |
| 缓存合并   | 将多次 key 拆解合并到一个结构中    | eg: 用 Hash 代替多个 key       |
| 限流/降级  | 防止 Redis 压力过大时系统崩溃    | 使用 fallback 逻辑兜底          |
##### 1.批量查询：`MGET` （多个 key 一次拿）
适用：多个不同的 key，需要一次性拿出数据。
```go
keys := []string{"user:1", "user:2", "user:3"}
vals, err := redisClient.MGet(ctx, keys...).Result()
```
优点：只发起一次 Redis 请求，节省网络 I/O
##### 2.使用 Hash 存结构化数据
假如你在一个业务中要查多个用户的某些字段：
```go
HGETALL user:info:123
HGET user:info:123 name
```
可以将多个字段存在一个 hash：
```go
HMGET user:info:123 name age gender
```
更适用于：
- 同类数据多个字段
- user、product、config 类型的数据
##### 3.使用 Pipeline 并发请求多个命令（异步批处理）
```go
pipe := redisClient.Pipeline()
cmd1 := pipe.Get(ctx, "user:1")
cmd2 := pipe.Get(ctx, "user:2")
_, err := pipe.Exec(ctx)
```
优点：
- 多个命令批量发送，减少 RTT（网络往返）
- 执行速度比逐个发送更快
注意：**Pipeline 并非事务，也不保证原子性**
##### 4.引入本地缓存（比如 memory、sync.Map、groupcache）
- 对于秒级频率的 Redis 查询，可以加一层 **短周期内存缓存**
- 结合 Go 的 `sync.Map` 或者 `github.com/patrickmn/go-cache`
```go
// 第一次查 Redis，结果写入 go-cache
cache.Set("user:1", data, 1*time.Minute)
```
适合：
- 请求非常频繁
- 数据变更不频繁
- 小数据量热数据
##### 5.缓存合并（Cache Merge）
> 把多个 key 合并成一个 key 的结构，例如：

**不推荐：**
```go
get user:1:name
get user:1:age
get user:1:gender
```
**推荐：**
```go
hmget user:1 name age gender
```
**或者：**
```json
// user:1
{
  "name": "Tom",
  "age": 18,
  "gender": "male"
}
```
##### 6.预加载数据（Cache Preload）
对于已知在一段时间内需要访问的数据，可以**提前加载到缓存**，避免每次流程触发时都查一次。

- 例如：订单列表查询时会涉及所有店铺信息，可提前缓存所有店铺信息。
##### 7.设置合理 TTL + Lazy Refresh（延迟刷新）
- 对热点数据设置合理过期时间
- 缓存快过期时，后台异步更新（防止击穿）
```go
// 假设 TTL 剩余不足 10 秒，主动触发 refresh
if ttl < 10*time.Second {
    go RefreshCache(key)
}
```
##### 8.降级策略（Redis 挂了怎么办）
- 设置熔断器，Redis 查询失败后返回默认值或兜底方案
- 异常日志报警，自动重试机制
##### 实战组合建议
如果你在一个业务中要查很多用户、订单、配置项，可以：
- ✅ 先用 `MGET`/`HMGET` 批量拿
- ✅ 结合 `Pipeline` 并发处理异步请求
- ✅ 热数据维护在本地缓存层，1-5分钟内只访问本地
- ✅ 冷数据走 Redis，查不到时查 DB 然后更新 Redis

#### 12. redis 发布订阅者模型？
> Redis Pub/Sub 适合 **轻量级、实时通知** 的场景，但不保证可靠投递，**不适合做持久化消息队列**。生产中建议谨慎使用或改用 **Redis Stream / Kafka**
##### 发布订阅（Pub/Sub）模型简介
在 Redis 中，Pub/Sub 是一个**消息广播系统**，基于**频道（channel）** 传输消息：
- **发布者（Publisher）**：向频道发布消息
- **订阅者（Subscriber）**：订阅一个或多个频道，接收相关消息
特点：
- **实时性强**：发布后立即推送给所有订阅者
- **解耦**：发布者无需知道谁在订阅，订阅者无需关心发布来源
- **不存储**：消息是**即发即送即丢**，无历史缓存
##### 常用命令

| 命令                        | 描述              |
| ------------------------- | --------------- |
| `SUBSCRIBE channel`       | 订阅一个或多个频道       |
| `PUBLISH channel message` | 向频道发布消息         |
| `UNSUBSCRIBE channel`     | 取消订阅频道          |
| `PSUBSCRIBE pattern*`     | 订阅通配符频道（支持模式匹配） |
##### 工作流程示意图
```lua
           +------------------+
           |   Publisher A    |
           +------------------+
                 |
                 |  publish("news", "🔥爆炸新闻")
                 ↓
          Redis Channel: "news"
         ↙         ↓           ↘
+------------+ +-------------+ +------------+
| Subscriber | | Subscriber  | | Subscriber |
|     X      | |     Y       | |     Z      |
+------------+ +-------------+ +------------+
```
所有订阅者都会收到 `"🔥爆炸新闻"` 这条消息
##### 使用场景

| 场景       | 描述             |
| -------- | -------------- |
| 实时通知系统   | 聊天消息、告警推送、事件广播 |
| 多服务协同    | 微服务间事件通知       |
| 游戏房间广播   | 玩家操作同步、事件分发    |
| 热点数据变更通知 | 缓存更新、配置变更通知    |
##### 缺点

| 问题        | 说明                           |
| --------- | ---------------------------- |
| ❌ 不持久化    | 消息不会落盘，订阅者不在线就**收不到**        |
| ❌ 不可靠投递   | 无确认机制，**容易消息丢失**             |
| ❌ 无队列积压能力 | 不能保证消费顺序、不能重试                |
| 单线程       | Redis 主线程处理订阅逻辑，订阅者多时容易阻塞主流程 |


##### 替代方案

| 替代品            | 特点                           |
| -------------- | ---------------------------- |
| Redis Stream   | 支持消费组、消息确认、持久化（比 Pub/Sub 强大） |
| Kafka、RabbitMQ | 专业消息队列，适合大规模异步通信             |
| NATS、RocketMQ  | 更适合微服务架构                     |
