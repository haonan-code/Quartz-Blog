## 一、基础
#### char 和 varchar 区别
**char 是定长字符串类型，其长度是固定的，不足时补充空格，空间浪费，但读取时效率高。**
**varchar 是可变长字符串类型，其长度是根据存入变量的大小进行变化的，节省存储空间，减少查询时的消耗。读取时慢，需读取长度信息。**
#### 谈一下 MySQL 和 Redis 的特点和区别
**MySQL 是关系型数据库，主要负责将数据持久化到硬盘，常用于数据存储场景**
- **数据结构化与完整性：** 数据以表格形式组织，每个表有固定的列和行。通过主键、外键、唯一约束等机制，可以确保数据的完整性和一致性。
- **ACID 特性：** 严格遵循 **ACID** 特性，这意味着事务是原子性的（要么全成功，要么全失败）、数据是持续一致的、事务之间是隔离的、并且一旦提交数据就不会丢失。这对于需要高可靠性和数据完整性的应用（如金融交易）至关重要。
- **复杂查询能力：** 支持复杂的 SQL 查询，包括连接 (JOIN)、聚合 (GROUP BY)、排序 (ORDER BY) 等，能够高效地处理结构化数据的复杂查询需求。
- **持久化存储：** 数据存储在磁盘上，即使系统重启或崩溃，数据也不会丢失。
- **成熟稳定：** 拥有庞大的社区支持、丰富的工具生态系统和多年的生产环境验证，非常成熟和稳定。
- **适用场景：** 适合存储需要强一致性、事务支持、复杂关联查询的结构化数据，例如用户账户、订单信息、博客文章等。
**Redis 是内存数据库，保存的是键值对，单线程模型但速度快，经常用于缓存、消息队列等场景**
- **极致读写性能：** 由于数据存储在内存中，Redis 的读写速度非常快，通常能达到每秒数万甚至数十万次的请求。
- **支持多种数据结构：** Redis 还支持多种复杂的数据结构，如字符串 (Strings)、哈希 (Hashes)、列表 (Lists)、集合 (Sets)、有序集合 (Sorted Sets) 等
- **原子操作：** Redis 的所有操作都是原子性的，这意味着即使在并发环境下，操作也不会被中断，保证了数据的一致性。
- **可选的持久化：** 虽然主要在内存中操作，但 Redis 也提供了 RDB（快照）和 AOF（追加文件）两种持久化机制，可以将内存中的数据写入磁盘，以防止数据丢失。
- **发布/订阅模式：** 内置了 Pub/Sub 功能，可以用作简单的消息队列。
- **适用场景：** 适用于对读写性能要求极高的场景，如缓存、实时排行榜、计数器、会话存储、消息队列、实时数据分析等。
#### MySQL 存储引擎 - 哪个支持事务
**InnoDB**：支持事务，默认引擎，**支持事务、行级锁、外键、高并发**
**MyISAM**：不支持事务，**支持全文索引，性能较好，但不支持事务和行锁**
#### 主键和外键
##### 主键
> 主键是用来**唯一标识一行记录**的字段，不能重复、不能为 NULL。

**作用：**
- 唯一标识一行记录（**不能重复、不能为 NULL**）
- 是每张表中最核心的字段，一般用于查询、关联、更新等操作
**特点：**

| 属性   | 描述                 |
| ---- | ------------------ |
| 唯一性  | 表中所有主键值必须唯一        |
| 非空   | 主键字段不能为 `NULL`     |
| 默认索引 | 主键自动创建聚簇索引（InnoDB） |
| 唯一存在 | 一张表只能有 **一个主键**    |
##### 外键
> 外键是**用来关联其他表的主键**，用于建立表与表之间的关系。

**作用：**
- 建立表与表之间的**关系**
- 外键字段引用另一个表的主键或唯一键，用于**约束数据的一致性**
**特点：**

| 属性        | 描述                                 |
| --------- | ---------------------------------- |
| 关联性       | 引用另一张表的主键或唯一键                      |
| 被引用限制     | 插入外键时，必须保证对应主键存在                   |
| 支持级联操作    | 可以设置 `ON DELETE` / `ON UPDATE` 的行为 |
| InnoDB 支持 | **MyISAM 不支持外键**，InnoDB 才支持        |

## 二、 MySQL 锁机制
####  mysql 锁机制
| 分类    | 锁类型                 | 说明                 |
| ----- | ------------------- | ------------------ |
| 按操作对象 | 表锁（Table Lock）      | 锁定整张表，开销小，粒度粗      |
|       | 行锁（Row Lock）        | 锁定记录，开销大，粒度细，支持高并发 |
| 按操作行为 | 共享锁（S Lock）         | 读操作，多个事务可以同时加      |
|       | 排他锁（X Lock）         | 写操作，只能一个事务加        |
| 其他锁   | 意向锁（Intention Lock） | 表级锁，标记事务意图，配合行锁使用  |
|       | Gap锁、Next-Key锁      | InnoDB 特有，防止幻读     |
#####  表锁（Table Lock）
表锁是 MySQL 层面的锁，由 **MyISAM、MEMORY** 存储引擎使用，InnoDB 也支持但很少用。
- **读锁**（共享锁）：允许其他线程读，但不允许写。
- **写锁**（排他锁）：阻塞其他线程的读和写。
```sql
LOCK TABLES table_name READ;   -- 加读锁
LOCK TABLES table_name WRITE;  -- 加写锁
UNLOCK TABLES;                 -- 释放锁
```
适合读多写少的场景，简单但并发性差。
#####  行锁（Row Lock）
行锁是 **InnoDB** 存储引擎支持的锁类型，**默认在事务中自动加锁**。
**行锁加锁方式**
- **共享锁（S锁）**：事务只能读，不允许写
- **排他锁（X锁）**：事务可读可写，其它事务不能读写
```sql
-- 手动加锁
SELECT * FROM users WHERE id=1 LOCK IN SHARE MODE; -- 加 S 锁
SELECT * FROM users WHERE id=1 FOR UPDATE;          -- 加 X 锁
```
InnoDB 的行锁是基于 **索引** 实现的，没有索引就会退化为表锁！
####  乐观锁悲观锁
#####  乐观锁
假设操作时不会冲突，只是提交时检查是否被修改过，冲突再回滚或重试。
**特点**
- **不会加数据库层面锁**
- 依赖业务控制，例如**版本号机制** 或 **时间戳机制**
- 适合**读多写少**、冲突不频繁的场景
#####  悲观锁
每次操作都假设会发生并发冲突，故在每次操作前就会加锁，其他事务不能同时操作
**特点**
- 通常是数据库层面的**加锁机制**
- 适合**写多、冲突高**的场景
- 常依赖于 `SELECT ... FOR UPDATE` 或 `LOCK IN SHARE MODE`
**示例：使用 `FOR UPDATE` 加悲观锁**
```sql
BEGIN;

SELECT stock FROM products WHERE id = 1 FOR UPDATE;

-- 假设 stock = 10
UPDATE products SET stock = stock - 1 WHERE id = 1;

COMMIT;
```
这里的 `FOR UPDATE` 会对查询的行加排他锁，其他事务不能读写该行，直到事务提交。


## 三、事务
#### 事务是什么？
事务（Transaction）是指一个**不可分割的逻辑工作单元**，包含一系列数据库操作，这些操作要么**全部成功执行，要么全部失败回滚**，不存在中间状态，保证数据的一致性和完整性。
#### mysql事务四大特性
| 特性                       | 含义                                |
| ------------------------ | --------------------------------- |
| **A - 原子性（Atomicity）**   | 事务中的所有操作要么全部成功，要么全部失败。            |
| **C - 一致性（Consistency）** | 事务执行后，数据库从一个一致状态转变到另一个一致状态。       |
| **I - 隔离性（Isolation）**   | 并发执行的事务之间互不干扰，一个事务的内部操作对其他事务是隔离的。 |
| **D - 持久性（Durability）**  | 一旦事务提交，所做的修改就会永久保存到数据库中           |
#### 事务隔离级别
##### 事务并发问题
**脏读**：读到其他事务还没提交的修改
**幻读**：同一事务内，前后两次查询，返回的结果集行数不同
**不可重复读**：同一事务内，前后两次读取同一行数据不一致
##### 事务隔离级别约束
| 隔离级别                   | 约束策略     | 解决的问题      |
| ---------------------- | -------- | ---------- |
| READ UNCOMMITTED（读未提交） | 几乎不加限制   | 啥都不解决      |
| READ COMMITTED（读已提交）   | 只能读已提交版本 | 防止脏读       |
| REPEATABLE READ（可重复读）  | 同一事务快照一致 | 防止脏读、不可重复读 |
| SERIALIZABLE（串行化）      | 串行执行     | 全部解决       |
> MySQL（InnoDB 引擎）**默认隔离级别是：REPEATABLE READ（可重复读）**
#####  READ UNCOMMITTED（读未提交）
- 事务能看到**其他事务未提交**的数据（脏读）。
- 基本不加锁，性能最好，但安全性最低。
#####  READ COMMITTED（读已提交）
- 每次查询都能看到**已提交的数据**
- 避免了脏读
- 但不能避免**不可重复读**：同一事务内多次读到的结果可能不同
#####  REPEATABLE READ（可重复读）MySQL 默认
- 事务开始后看到的记录**始终一致**
- 通过 **MVCC** 实现一致性快照
- 避免不可重复读
- ⚠️ 幻读仍可能发生，但 InnoDB 使用 **Next-Key Lock** 解决了
#####  SERIALIZABLE（串行化）
- 最严格的隔离级别
- 所有事务 **串行执行**
- 会对读的每一行加**共享锁**，导致并发性能极差
- 避免所有并发问题：脏读、不可重复读、幻读全部防止
#### 事务隔离级别是怎么实现的
隔离级别的实现主要有**读写锁**和**MVCC( Multi-Version Concurrency Control )多版本并发处理方式**。
- **读未提交**：它是性能最好，也可以说它是最野蛮的方式，因为它压根就不加锁，所以根本谈不上什么隔离效果，可以理解为没有隔离。
- **读已提交**：在读已提交隔离级别下，在事务中每一次执行快照读时生成ReadView。多个事物有多个ReadView , 事务没有结束之前只能读取自己的ReadView , 实现了读已提交 , 不能读取到其他事物未提交的数据
- **可重复读**：在可重复读隔离级别下，仅在事务中第一次执行快照读时生成ReadView，后续复用该ReadView。 而**Repeatable Read** 是可重复读，在一个事务中，执行两次相同的select语句，查询到的结果是一样的
- **串行化**：读的时候加共享锁，也就是其他事务可以并发读，但是不能写。写的时候加排它锁，其他事务不能并发写也不能并发读。

## 四、索引
#### 索引的数据结构
在 MySQL 中，索引是为了**加快数据查找速度而构建的数据结构**，其本质就是为了**降低查询的时间复杂度**。
常见的索引数据结构主要有两种：
##### B+ 树（最常用，InnoDB 默认使用）
**结构特点：**
- 所有值都存储在**叶子节点**，并且按顺序排列
- **叶子节点之间有链表指针**，支持范围查询
- 非叶子节点只存储键（用于引导查询），不存数据
- 每个节点可存多个键（即“多叉树”）
**优点：**
- 查询性能稳定：查询时间复杂度为 O(log<sub>m</sub>N)，m 为树的阶
- 支持范围查询：因为叶子节点有顺序链表
- IO 次数少：每个节点存很多键，层数较少（一般 2~4 层）
##### Hash（哈希索引）
**结构特点：**
- 基于哈希函数，将键映射到槽位（数组下标）
- 哈希值 → 数据地址
- 使用如链表、拉链法解决冲突
**优点：**
- 查询效率极高，时间复杂度约 O(1)
- 适合**等值查询**
**使用场景：**
- Memory 存储引擎默认使用
- 适合**精确匹配查询**，如字典表、验证码表等

#### 索引是什么
> 索引是数据库中用于**快速查找数据**的结构，相当于书的“目录”或“电话簿”。
#### 索引类型

| 索引类型     | 说明                            | 示例                                      |
| -------- | ----------------------------- | --------------------------------------- |
| **主键索引** | `PRIMARY KEY`，唯一 + 非空，默认建聚簇索引 | `id INT PRIMARY KEY`                    |
| **唯一索引** | `UNIQUE`，值不能重复，但可以为 `NULL`    | `email VARCHAR(100) UNIQUE`             |
| **普通索引** | 最基础的索引，没有唯一性限制                | `CREATE INDEX idx_name ON users(name);` |
| **联合索引** | 多个字段组成的索引，适用于多条件查询            | `INDEX idx_name_email(name, email)`     |
| **全文索引** | 用于全文搜索，适合大文本（InnoDB ≥ 5.6）    | `FULLTEXT(title, content)`              |
| **前缀索引** | 只索引字段的前 N 个字符，节省空间            | `INDEX idx_prefix(name(10))`            |

#### 怎么使用，使用过哪些索引，还有哪些索引
##### 创建索引
```sql
-- 普通索引
CREATE INDEX idx_username ON users(username);

-- 唯一索引
CREATE UNIQUE INDEX idx_email ON users(email);

-- 联合索引
CREATE INDEX idx_user ON users(name, age);

-- 全文索引（InnoDB 5.6+ 支持）
CREATE FULLTEXT INDEX idx_text ON articles(title, content);
```
##### 删除索引
```sql
DROP INDEX idx_username ON users;
```
##### 查看索引
```sql
SHOW INDEX FROM users;
```
##### 索引是否被使用
```sql
EXPLAIN SELECT * FROM users WHERE name = 'alice';
```
- 看 `key` 字段是否用了某个索引
- 看 `type` 字段是不是 `ref`、`range`、`const`（都比 `ALL` 好）

#### MySQL 索引是用什么数据结构实现的？
B+树、Hash表（哈希索引）
#### 说说 B+ 树的特点。
> B+ 树是一种**多路平衡查找树**，结构特别适合磁盘存储，它的 **宽度大、深度小、顺序性强**，可以**极大地减少磁盘 I/O 次数，提高查询效率**。

特点：
- **多路搜索树**：每个节点可有多个子节点，不是二叉（M阶树）
- **所有值都在叶子节点**：非叶子节点仅用于引导查找（只存 key，不存 value）
- **叶子节点有序链表连接**：叶子节点按 key 排序，并通过指针连接，方便范围查询
- **所有叶子节点在同一层**：保证查找路径长度一致，查询效率稳定
- **磁盘友好**：每个节点可存多个 key，减少磁盘 I/O 次数
- **支持范围查找**：顺序访问叶子链表即可，高效支持 `BETWEEN`、`<`、`>` 等操作

#### B+树原理和B树对比
##### B+树原理
> **B+ 树（Balanced Plus Tree）是一种多路平衡查找树，是 B-树的变种**，专门优化用于**磁盘存储**、**范围查询**、**高并发读写**等数据库场景。
##### 与B树对比
| 比较点    | B树            | B+树 ✅ MySQL 使用    |
| ------ | ------------- | ----------------- |
| 数据存储位置 | 所有节点都可以存储数据   | **仅叶子节点存数据**      |
| 叶子节点连接 | 无链表连接         | **叶子节点有链表连接**     |
| 范围查询   | 需要中序遍历整棵树     | **顺序遍历叶子节点**      |
| 查找效率   | 可能提前返回        | **必须查到叶子节点**，更稳定  |
| 非叶子节点  | 存 key + value | **只存 key，用于索引导航** |

#### MySQL 乐观锁和悲观锁有什么区别？怎么实现？
##### 是什么？
**悲观锁：** 假设每次操作都会发生冲突，**先加锁再操作**，防止其他人并发访问
**乐观锁：** 假设并发冲突是极少数，**不加锁，先操作，提交时校验是否冲突**
##### 区别

| 对比项   | **悲观锁** 🔒                          | **乐观锁** 🛡️             |
| ----- | ----------------------------------- | ----------------------- |
| 原理    | 操作前加锁，防止并发写入                        | 操作前不加锁，提交时校验是否被修改       |
| 实现方式  | 使用数据库锁机制（如 `SELECT ... FOR UPDATE`） | 使用**版本号、时间戳、数据快照**等方式实现 |
| 并发性能  | 低，容易产生锁等待、死锁                        | 高，避免锁竞争，适合读多写少场景        |
| 避免脏数据 | 自动防止                                | 通过版本对比防止                |
| 使用场景  | 写操作频繁、冲突多，如银行转账                     | 写冲突较少，如商品浏览数更新、用户信息修改   |

##### 实现
**悲观锁实现（InnoDB 引擎）**
> InnoDB 支持行级锁，可通过 `SELECT ... FOR UPDATE` 实现悲观锁
```sql
BEGIN;

-- 加悲观锁：锁住该行，其它事务需等待
SELECT * FROM products WHERE id = 1 FOR UPDATE;

-- 修改库存
UPDATE products SET stock = stock - 1 WHERE id = 1;

COMMIT;
```
- ✅ 数据库层加锁（行锁）
- ❌ 如果多个事务并发执行，后发请求将等待前面释放锁
**乐观锁实现（通过版本号或更新时间字段）**
> 不依赖数据库锁机制，而是通过“**版本字段 version**”或“**更新时间 updated_at**”判断数据是否被改动

示例一：使用`version`字段
```sql
-- 第一次读取数据
SELECT id, stock, version FROM products WHERE id = 1;

-- 假设读到 version = 3，现在尝试更新
UPDATE products
SET stock = stock - 1,
    version = version + 1
WHERE id = 1 AND version = 3;
```
- ✅ 如果没有并发冲突，version == 3，更新成功
- ❌ 如果有并发更新，version 已变为 4 → 更新失败，受影响行数为 0
示例二：使用`updated_at`字段
```sql
UPDATE users
SET nickname = 'Alice', updated_at = NOW()
WHERE id = 1 AND updated_at = '2025-07-06 12:00:00';
```
##### 适用场景
> **悲观锁：** 提前上锁防冲突，适合**冲突多、写操作频繁**的场景  
   **乐观锁：** 不加锁靠校验，适合**冲突少、性能优先**的场景

| 场景            | 建议使用          |
| ------------- | ------------- |
| 银行账户转账、库存扣减   | ✅ 悲观锁（数据强一致性） |
| 用户昵称修改、点赞计数更新 | ✅ 乐观锁（冲突概率低）  |
| 频繁读写但要求性能     | ✅ 乐观锁配合重试机制   |
| 高并发写操作，冲突概率高  | ✅ 悲观锁，避免写入乱序  |

#### 锁是如何实现数据同步的？
锁的核心思想是**控制对共享资源的排他性访问**。当一个协程获得了锁，它就可以**独占**地访问被锁保护的资源。其他想要访问这个资源的协程，必须等待锁被释放。
##### 互斥锁（Mutex）
这是最常见的锁类型，也是实现数据同步的基石。
**工作原理：**
- 当一个协程想要访问**共享资源**时，它首先尝试**获取锁**。
- 如果锁没有被其他协程持有，该协程成功获取锁，然后可以安全地访问共享资源。
- 在访问完成后，该协程会**释放锁**。
- 如果锁已经被其他协程持有，那么尝试获取锁的协程会被**阻塞**（暂停执行），直到锁被释放为止。
- 当锁被释放时，被阻塞的协程中，通常会有一个（或多个）协程被唤醒，并再次尝试获取锁。
**作用**：确保在任何给定时刻，只有一个协程能够访问被保护的代码区域（通常称为**临界区 Critical Section**），从而避免竞态条件，保证数据的一致性。
##### 读写锁
互斥锁虽然能保证安全，但它比较粗暴：即使是只读操作，也会被阻塞。在读多写少的场景下，这会严重影响性能。读写锁就是为了解决这个问题而生。
**工作原理：**
- 允许多个协程**同时获取读锁**（共享锁），因为多个读取者同时读取数据是安全的，不会造成数据不一致。
- 只允许一个协程**获取写锁**（排他锁），当有写锁存在时，任何读锁和写锁都无法被获取。
- 当有读锁存在时，写锁无法被获取。
- 当有写锁存在时，读锁和写锁都无法被获取。
**作用**：提高并发度，特别适用于读操作远多于写操作的场景。
##### 其他同步机制
- **条件变量 (Condition Variable):** 通常与互斥锁配合使用，用于在某个条件不满足时，让协程等待；当条件满足时，通知等待的协程。它本身不提供互斥访问，而是提供线程/协程之间的通信机制。
- **信号量 (Semaphore):** 控制对共享资源的访问数量。可以限制同时访问某个资源的协程数量，而不仅仅是1个。
- **原子操作 (Atomic Operations):** 对于简单的操作（如整数加减、比较并交换等），硬件和CPU提供了原子性操作的指令。这些操作在执行时不会被中断，比使用锁的开销更小，更高效。
- **通道 (Channels - Go 语言特有):** Go 语言提倡通过**通信来共享内存，而不是通过共享内存来通信**。Channel 是 Go 中用于协程间安全通信的重要机制，它在数据传输过程中自动处理了同步问题，从而避免了直接使用锁的复杂性。
#### MySQL 聚簇索引和非聚簇索引是什么以及区别
##### 聚簇索引
**定义**：聚簇索引是**数据存储和索引顺序一致**的一种索引。  
在 MySQL 的 **InnoDB 存储引擎**中，**主键索引就是聚簇索引**。
**特点：**
- **数据行存储在主键顺序上**，即叶子节点保存的是**整行数据**。
- **一个表只能有一个聚簇索引**（因为数据只能按一种顺序存）。
- 如果你没有显式定义主键，InnoDB 会选择一个**唯一非空索引**作为聚簇索引；没有的话会自动创建一个隐藏的主键。
**优势：**
- 基于主键的查询效率高（因为数据就在索引里）
- 范围查询效率高（比如 `BETWEEN`、`<`、`>`）
**缺点：**
- 插入顺序依赖于主键，频繁插入可能导致**页分裂**。
- 更新主键代价高（会导致整行数据移动）
##### 非聚簇索引
**定义**：非聚簇索引的叶子节点中，存储的是对应行的**主键值**，并非整行数据。
**特点：**
- 一个表可以有**多个非聚簇索引**。
- 查询时先通过非聚簇索引找到主键，再通过主键去聚簇索引中找数据（称为**回表查询**）。
**示例：**
```sql
CREATE TABLE user (
  id INT PRIMARY KEY,           -- 聚簇索引
  name VARCHAR(50),             
  email VARCHAR(100),
  INDEX(name)                   -- name 是非聚簇索引
);
```
**执行**：
```sql
SELECT * FROM user WHERE name = 'Tom';
```
**流程**：
- 通过 name 的二级索引找到主键 id；
- 用 id 去聚簇索引中找到整行数据。
#### 覆盖索引
**定义**：如果一个索引包含了查询所需的所有列，就称该查询使用了**覆盖索引**，避免了“回表”操作。
示例：
```sql
SELECT name FROM user WHERE name = 'Tom';
```
如果创建了：
```sql
CREATE INDEX idx_name ON user(name);
```
这个查询就使用了 **覆盖索引**，因为查询的数据全部在 `idx_name` 索引中。
所以：
- 覆盖索引不是一种定义时的“索引类型”；
- 它是 **执行计划中是否使用了索引中已有的数据** 来满足查询的一个**优化手段**；
- 你可以通过 `EXPLAIN` 或 `EXPLAIN ANALYZE` 来观察是否用了 `covering index`。
#### 索引最左匹配原则
##### 介绍
对联合索引，MySQL 会按照索引中**从左到右的顺序**去匹配查询条件，只有**连续从最左边开始**的字段都能被使用，**中间一断，后面就不能用了**
##### 示例
建立一个联合索引：
```sql
CREATE INDEX idx_user ON user(name, age, gender);
```
这个索引的字段顺序是：`(name, age, gender)`
**能用索引的查询：**
```sql
-- 只用最左字段 name
SELECT * FROM user WHERE name = 'Tom'; ✅ 命中索引

-- 连续使用 name 和 age
SELECT * FROM user WHERE name = 'Tom' AND age = 20; ✅ 命中索引

-- 使用了全部字段
SELECT * FROM user WHERE name = 'Tom' AND age = 20 AND gender = 'M'; ✅ 命中索引
```
**不能使用整个索引的查询：**
```sql
-- 跳过了最左字段 name
SELECT * FROM user WHERE age = 20; ❌ 不能使用索引

-- name 用了范围查询，age/gender 不可用
SELECT * FROM user WHERE name > 'Tom' AND age = 20; ❌ 只用 name

-- 中间字段断开了（跳过 age）
SELECT * FROM user WHERE name = 'Tom' AND gender = 'M'; ❌ 只用 name
```

## 五、慢查询优化
### MySQL 的慢查询如何优化、优化方案
> **优化慢查询的核心：用正确的联合索引 + 覆盖索引，让 MySQL 少扫行、少回表、少锁等待。**
#### 慢查询（Slow Query）
执行时间超过阈值（默认 10 秒）的 SQL 被记录为慢查询
#### 定位慢 SQL
开启慢日志
```ini
slow_query_log = ON
long_query_time = 1
log_queries_not_using_indexes = ON
```
分析慢日志
```bash
mysqldumpslow slow.log
```

#### `EXPLAIN`看执行计划-找失效点
**使用`EXPLAIN`分析执行计划**
```sql
EXPLAIN SELECT * FROM users WHERE email = 'xx';
```
看关键字段：

| 字段      | 含义                                      |
| ------- | --------------------------------------- |
| `type`  | 访问类型（越左越好：const > ref > range > ALL）    |
| `key`   | 是否命中索引                                  |
| `rows`  | 扫描行数（越小越好）                              |
| `Extra` | 有 `Using index` / `Using filesort` 提示信息 |

所谓**失效点**，不是 MySQL 报错，而是指：
>执行计划中，本来可以用索引的地方，由于 SQL 写法不当，索引没被用上或只用了一部分。

常见失效点表现：

|字段|异常值|
|---|---|
|`type = ALL`|全表扫描|
|`key = NULL`|完全没走索引|
|`rows` 极大|扫描行数远超预期|
|`Extra = Using filesort`|排序没走索引|
|`Extra = Using temporary`|分组没走索引|

#### 常用优化方法（建索引、改 SQL、控事务）
##### 1. 建立正确的联合索引
等值在前，范围在后；过滤性强的靠左。
##### 2. 避免索引失效写法

| 错误写法                         |
| ---------------------------- |
| `where a+1=5`                |
| `where a like '%abc'`        |
| `where a = 100`（a 是 varchar） |
| `where left(a,3)='abc'`      |
##### 3. 用覆盖索引消灭回表
##### 4. LIMIT 大偏移优化
```sql
-- 慢
LIMIT 100000,20
-- 快
WHERE id > last_id LIMIT 20
```
把“数行”变成“跳转定位”。
##### 5. 排序 / 分组一定走索引
```sql
ORDER BY a,b
GROUP BY a,b
```
索引：
```sql
KEY idx_a_b(a,b)
```
##### 6. 拆分大 SQL
- 大 IN → 临时表 / join
- 超长事务 → 拆小事务
##### 7. 减少锁等待
- 控制事务时间
- 避免全表更新
- 必要时使用乐观锁
##### 8. 合理字段设计

|类型|建议|
|---|---|
|char / varchar|能短就短|
|int|不用 bigint|
|时间|用 datetime / timestamp|

## 六、数据表设计
#### mysql 设计表用于鉴权【rbac设计】
##### RBAC 是什么？
RBAC（Role-Based Access Control，**基于角色的访问控制**）是一种常见的权限模型，它通过**用户 → 角色 → 权限**的映射关系来控制用户访问资源的权限。
##### RBAC 的核心设计理念
> **用户不直接拥有权限**，而是**通过分配角色**来间接拥有权限。角色作为权限集合，可以复用和集中管理。
##### RBAC 数据库表设计（MySQL）
数据关系图：
```bash
users --< user_roles >-- roles --< role_permissions >-- permissions
```
**用户表**`users`
```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(64) NOT NULL UNIQUE,
    password VARCHAR(128) NOT NULL,
    email VARCHAR(128),
    status TINYINT DEFAULT 1, -- 1:启用, 0:禁用
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```
**角色表**`roles`
```sql
CREATE TABLE roles (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(64) NOT NULL UNIQUE,   -- 如 admin、editor、viewer
    description VARCHAR(255),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```
**权限表**`permissions`
```go
CREATE TABLE permissions (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(64) NOT NULL UNIQUE,     -- 权限标识，如 "view_user"
    resource VARCHAR(128),                -- URL、菜单、数据对象等
    method VARCHAR(16),                   -- HTTP 方法（GET、POST 等）
    description VARCHAR(255),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```
**用户-角色关联表**`user_roles`
```go
CREATE TABLE user_roles (
    user_id BIGINT,
    role_id BIGINT,
    PRIMARY KEY(user_id, role_id),
    FOREIGN KEY(user_id) REFERENCES users(id) ON DELETE CASCADE,
    FOREIGN KEY(role_id) REFERENCES roles(id) ON DELETE CASCADE
);
```
**角色-权限关联表**`role_permissions`
```sql
CREATE TABLE role_permissions (
    role_id BIGINT,
    permission_id BIGINT,
    PRIMARY KEY(role_id, permission_id),
    FOREIGN KEY(role_id) REFERENCES roles(id) ON DELETE CASCADE,
    FOREIGN KEY(permission_id) REFERENCES permissions(id) ON DELETE CASCADE
);
```
##### 使用流程示意
1.  **管理员分配角色**：将 `user_id` 与多个 `role_id` 建立关联。
2. **角色绑定权限**：通过 `role_permissions` 绑定权限。
3. **访问资源时检查权限**：
    - 查询用户拥有的角色
    - 再查角色拥有的权限
    - 匹配请求的路径和方法
##### RBAC 模型优势
| 优点       | 描述                                       |
| -------- | ---------------------------------------- |
| **易管理**  | 权限集中管理在角色上，变更权限时只需修改角色权限                 |
| **复用性高** | 角色可复用于多个用户，减少重复配置                        |
| **灵活扩展** | 可以扩展为 **RBAC 0/1/2/3 模型** 或结合 ABAC（基于属性） |
